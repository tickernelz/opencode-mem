نظام ذاكرة دائم لوكلاء البرمجة بالذكاء الاصطناعي يتيح الاحتفاظ بالسياق طويل الأمد عبر الجلسات باستخدام تقنية قاعدة بيانات متجهات محلية.

## الميزات الأساسية

قاعدة بيانات Turso/libSQL محلية مع بحث متجهات أصلي، ذكريات مشروع دائمة، تعلّم تلقائي لملف المستخدم، خط زمني موحّد للذاكرة والمطالبات، واجهة ويب كاملة الميزات، استخراج ذكي للذاكرة مستند إلى المطالبات، دعم مزودي ذكاء اصطناعي متعددين (OpenAI، Anthropic)، أكثر من 12 نموذج تضمين محلي، إزالة تكرار ذكية، وحماية خصوصية مدمجة.

## المتطلبات الأساسية

يستخدم هذا المكون الإضافي Turso المضمّن (`@tursodatabase/database`) مع متجهات `F32_BLOB` وبحث جيب التمام الدقيق عبر `vector_distance_cos`. لا حاجة لقاعدة بيانات متجهات منفصلة أو بناء SQLite مخصص.

**بيئة التشغيل الموصى بها:**

- Bun
- بيئة مكون OpenCode الإضافي القياسية
- اتصال بالإنترنت عند أول استخدام إذا كنت تستخدم نموذج التضمين المحلي الافتراضي، لأن النموذج يُنزَّل بواسطة `@huggingface/transformers`.
- لتثبيتات المصدر/التطوير، شغّل `bun install` قبل البناء أو الاختبار. حزمة المكون الإضافي المنشورة تثبّت تبعيات وقت التشغيل تلقائيًا عبر OpenCode.

**المنصات المختبرة في CI:** Linux وWindows وmacOS 15 / macOS 26 على Apple Silicon (`darwin/arm64`). **Intel Mac (`darwin/x64`) غير مدعوم** — `@tursodatabase/database` وإصدارات `onnxruntime-node` الثابتة لا توفّر ربطًا أصليًا لـ x64. إصدارات macOS الأقدم ليست مستبعدة من تلك المصفوفة؛ هي ببساطة خارج مجموعة مشغّلات GitHub الحالية المستضافة.

**ملاحظات:**

- تُخزَّن تضمينات المتجهات وتُبحث مباشرة في Turso؛ عمليات الإدراج تخزّن متجهات `F32_BLOB` لترتيب جيب التمام الدقيق.
- يستخدم بحث المتجهات مسافة جيب التمام الدقيقة عبر `vector_distance_cos` (بدون DiskANN / فهرس تقريبي)، مع ترتيب هجين اختياري بالكلمات المفتاحية عند توفير سلسلة استعلام (`@tursodatabase/database` لا يوفّر FTS5).
- تستخدم عمليات البحث عن الجلسات عمود `session_id` مفهرسًا (مُعبَّأ رجعيًا من `metadata.sessionID` في المخطط v2).
- الالتقاط التلقائي وتعلّم ملف المستخدم يتطلبان مزود ذكاء اصطناعي يمكنه إرجاع مخرجات منظمة/استدعاء أدوات. بحث/إضافة/قائمة الذاكرة ما زالت تعمل بدون إعداد مزود الالتقاط التلقائي.

### توقعات الأجهزة / الموارد

opencode-mem **لا** يتطلب وحدة معالجة رسومات (GPU). تعمل التضمينات المحلية على وحدة المعالجة المركزية عبر `@huggingface/transformers` وONNX (لا يوجد خلفية MLX). لا حاجة لذاكرة فيديو إضافية (VRAM).

| عبء العمل                                                      | الموارد الإضافية النموذجية                                                                                                                                                                                                                                                  |
| -------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **التضمينات المحلية** (الافتراضي `Xenova/nomic-embed-text-v1`) | حوالي **0.5–2 GB RAM** أثناء تحميل النموذج، حسب معرّف Hugging Face الذي تختاره. أول استخدام ينزّل النموذج؛ توجد ذاكرة التخزين المؤقت على القرص تحت `{storagePath}/.cache` (الافتراضي `~/.opencode-mem/data/.cache`) وغالبًا تكون **مئات الميجابايت إلى ~1–2 GB** لكل نموذج. |
| **التضمينات البعيدة** (`embeddingApiUrl` + `embeddingApiKey`)  | ذاكرة ML محلية ضئيلة — فقط عبء المكون الإضافي + Turso.                                                                                                                                                                                                                      |
| **قاعدة البيانات / المكون الإضافي**                            | Turso/libSQL على القرص تحت `storagePath`. ينمو الحجم بعدد الذكريات المخزّنة، وليس بذاكرة GPU.                                                                                                                                                                               |

تظل حدود المنصات أعلاه سارية (لا يوجد Intel Mac `darwin/x64`؛ استخدم Apple Silicon أو Linux أو Windows أو نقطة نهاية تضمين بعيدة). انظر [اختيار / إعداد التضمينات](#اختيار--إعداد-التضمينات).

### الترقية من أجزاء SQLite القديمة

عند البدء يُستأنف استرداد عمليات تبديل إعادة التضمين المتقطعة، ويحوّل فهارس libSQL DiskANN إلى محرك Turso الحالي، ثم يتحقق من مخطط الجزء القديم أو يرقّيه. يعمل تحويل المحرك حتى عندما يحمل المخزن بالفعل علامة ترحيل قديمة مكتملة، ويحافظ على المتجهات المخزّنة دون إعادة تضمين. تُنسخ كل قاعدة بيانات محوَّلة احتياطيًا باسم `<database>.pre-tursodb-<timestamp>.bak`.

على macOS وLinux، يمكن لعدة جلسات OpenCode مشاركة نفس `storagePath` عبر `multiprocess_wal` التجريبي من Turso (يجب أن يستخدم كل عملية نفس الوضع — أعد تشغيل جميع الجلسات بعد الترقية). على Windows يرفض المحرك ذلك العلم، لذا يمكن لجلسة OpenCode واحدة فقط امتلاك قواعد بيانات الذاكرة في وقت واحد.

عند أول تشغيل بعد الترقية، يرحّل opencode-mem تلقائيًا قواعد بيانات أجزاء الذاكرة الحالية إلى تنسيق متجهات Turso/libSQL الأصلي:

- يُنسخ كل جزء احتياطيًا باسم `<shard>.db.legacy.bak` قبل إعادة الكتابة
- يُتتبَّع التقدم لكل جزء في `<shard>.db.turso-migrate.json`
- تُكتب علامة عالمية `.turso-migrated` فقط بعد التحقق الناجح من جميع الأجزاء
- لا تشغّل عدة نسخ من OpenCode ضد نفس `storagePath` أثناء الترحيل؛ يمنع ملف قفل (`.turso-migrate.lock`) الترحيل المتزامن
- تستخدم ترحيلات الأبعاد اليدوية `.turso-operation.lock`؛ ترفض عمليات المكون الإضافي الأخرى كتابات الذاكرة الجديدة حتى ينتهي الترحيل

إذا انقطع الترحيل، يستأنف التشغيل التالي تلقائيًا من النسخة الاحتياطية.

إذا أصبح جزء غير متوافق (مثلًا بعد تغيير `embeddingDimensions`)، تُحظر الكتابات وتُترك قاعدة البيانات الأصلية دون مساس. استخدم ترحيل إعادة التضمين في واجهة الويب لبناء بديل والتحقق منه قبل تبديله في مكانه. يبقى الجزء السابق متاحًا باسم `<shard>.db.pre-reembed-<pid>-<timestamp>.bak`.

## ترحيلات المخطط

تُرقّى أجزاء Turso المحلية وقواعد البيانات المساعدة (`metadata.db`، `user-prompts.db`، `user-profiles.db`، `ai-sessions.db`) بترحيلات `PRAGMA user_version` مرتبة في `src/services/turso/schema-migrations.ts`. الترحيلات عديمة الأثر عند التكرار: تشغيل المكون الإضافي يطبّق فقط الإصدارات المعلقة.

## البدء

لـ OpenCode v2، أضف الحزمة إلى قائمة `plugins` الأصلية:

```jsonc
{
  "plugins": ["opencode-mem@latest"],
}
```

يحمّل OpenCode أيضًا رفيق الحزمة `./tui` تلقائيًا حتى
تظهر إشعارات الالتقاط التلقائي / الملف / الأخطاء في TUI (مكونات الخادم
الإضافية لا يمكنها استدعاء `ui.toast` مباشرة). لا تحتاج إدخالًا ثانيًا في
`plugins`. إذا شغّلت TUI من سطر الأوامر فقط ضد خادم OpenCode بعيد،
سجّل `opencode-mem/tui` في قائمة مكونات ذلك CLI (مثلًا
`cli.json`) حتى يتمكن الرفيق من الاشتراك في أحداث toast عبر RPC.

لـ OpenCode v1، أضف نقطة الدخول الافتراضية إلى إعداداتك في
`~/.config/opencode/opencode.json`:

```jsonc
{
  "plugin": ["opencode-mem@latest"],
}
```

مع `@latest` (أو نطاق semver) و`autoUpdate: true` في `opencode-mem.jsonc` (الافتراضي)، يمسح المكون الإضافي تثبيت OpenCode المخزَّن مؤقتًا عندما يتوفر إصدار npm أحدث ويطلب منك إعادة التشغيل. الإصدارات المثبتة مثل `opencode-mem@2.26.0` لا تُحدَّث تلقائيًا أبدًا.

### سياق الذاكرة التلقائي على OpenCode v2

يوفّر مكون v2 الإضافي سياق ذاكرة تلقائيًا عبر سياق نظام النموذج.
لا تُضاف هذه الكتل إلى مطالبة المستخدم المؤلفة ولا تُخزَّن في نص المحادثة.
مع `chatMessage.injectOn: "first"` (الافتراضي)، يُحتفظ بالسياق الأولي للجلسة
عبر دورات المستخدم وخطوات النموذج. مع `"always"`، يُحدَّث عند كل
دورة مستخدم مؤلفة.

بعد إعادة تشغيل المضيف أو المكون الإضافي، تعيد الجلسة المستأنفة بناء سياقها من
مخزن الذاكرة الحالي عند طلب النموذج التالي، حتى لو لم تصل مطالبة مستخدم جديدة.
قد يختلف السياق المعاد بناؤه عن الأصلي مع تطوّر الذكريات والملف.
لا تلتقط الاستعادة مطالبة مستخدم اصطناعية ولا تخزّن نسخة ثانية من
نص الذاكرة في تخزين مكون OpenCode الإضافي. يُبطل الضغط (compaction) السياق التلقائي
المخزَّن مؤقتًا؛ وتستمر أيضًا استعادة ذاكرة الضغط الحالية في العمل.

### استخدام نسخة محلية

لتشغيل المكون الإضافي من نسخة مصدر محلية بدل إصدار npm، نفّذ `bun install && bun run build` في النسخة، ثم وجّه قائمة `plugins` إلى مجلد النسخة:

```jsonc
{
  "plugins": ["/absolute/path/to/opencode-mem"],
}
```

وجّه إلى جذر الحزمة، وليس إلى `dist/` أو ملف واحد. يحلّ OpenCode مكونًا إضافيًا من مجلد بالرجوع إلى `<directory>/index` (OpenCode لا يقرأ `package.json` `exports`/`main` لمواصفات مسار في الإصدارات الحالية)، لذا يوفّر هذا المستودع `index.js` رفيعًا في الجذر يعيد تصدير نقطة دخول v2 المبنية من `dist/plugin.js`، و`tui.js` في الجذر يعيد تصدير `dist/tui.js` لرفيق TUI. يُرفض المسار إلى ملف (`configured plugin path must be a directory`)، ويُتخطى المجلد بدون `index.js` في الجذر بصمت.

### تشفير قاعدة البيانات الاختياري في حالة السكون

فعّل تشفير AES-256-GCM لأجزاء Turso المحلية في `~/.config/opencode/opencode-mem.jsonc`:

```jsonc
{
  "databaseEncryptionEnabled": true,
}
```

عند أول تشغيل ينشئ المكون الإضافي `~/.config/opencode/opencode-mem-db.key` (مفتاح hex بطول 32 بايت، `chmod 600`) ويرحّل الأجزاء النصية الحالية. تجاوز بـ `"databaseEncryptionKey": "env://OPENCODE_MEM_DB_KEY"` أو `"file://~/path/to.key"` إذا كنت تدير المفتاح بنفسك. فقدان المفتاح يعني أن قواعد البيانات المشفّرة لا يمكن فتحها.

**Windows:** استخدم `%USERPROFILE%\.config\opencode\opencode.json` (مثلًا `C:\Users\<you>\.config\opencode\opencode.json`). هذا المكون الإضافي **لا** يقرأ `%APPDATA%` أو `%LOCALAPPDATA%` لمدخل مكون OpenCode الإضافي — ضع الملف تحت `.config\opencode` في ملف تعريف المستخدم، ثم أعد تشغيل OpenCode. إذا لم يظهر المكون الإضافي، أكّد ذلك المسار وأعد التشغيل مجددًا.

يُنزَّل المكون الإضافي تلقائيًا عند التشغيل التالي.

## كيفية الاستخدام اليومي

**لا** تحتاج أن تطلب من OpenCode أن «يتذكّر» أشياء حتى يعمل المكون الإضافي. مع الإعدادات الافتراضية، تُبنى الذاكرة أثناء عملك.

### سير العمل اليومي النموذجي

1. فعّل المكون الإضافي (انظر [البدء](#البدء)) وأعد تشغيل OpenCode.
2. أعد مزود ذكاء اصطناعي للالتقاط التلقائي — الموصى به: `opencodeProvider` + `opencodeModel` (أو `"opencodeModel": "inherit"`). التفاصيل تحت [مزود الذكاء الاصطناعي للالتقاط التلقائي](#مزود-الذكاء-الاصطناعي-للالتقاط-التلقائي).
3. اعمل بشكل طبيعي في OpenCode. عندما تصبح الجلسة خاملة، يستخرج الالتقاط التلقائي السياق التقني الجدير بالتذكر ويخزّنه.
4. في الجلسات اللاحقة، تُحقن الذكريات ذات الصلة في السياق (انظر إعدادات `chatMessage` / الضغط). تصفّحها أو عدّلها في واجهة الويب على `http://127.0.0.1:4747`.
5. استخدم أداة `memory` عندما تريد تخزين شيء أو استرجاعه فورًا (انظر [أمثلة الاستخدام](#أمثلة-الاستخدام)).

### الذاكرة التلقائية مقابل اليدوية

| النهج                                                         | متى يعمل                                   | ما تفعله                                                                                   |
| ------------------------------------------------------------- | ------------------------------------------ | ------------------------------------------------------------------------------------------ |
| **الالتقاط التلقائي** (`autoCaptureEnabled: true`، الافتراضي) | بعد دورات المحادثة عندما تصبح الجلسة خاملة | لا شيء — الاستخراج تلقائي                                                                  |
| أداة / أوامر `memory` **اليدوية**                             | عند الطلب                                  | `add`، `search`، `list`، `profile`، `forget`، `list-shards`، `migrate`، `export`، `import` |

ما زال البحث/الإضافة/القائمة اليدوية تعمل حتى لو لم يكن للالتقاط التلقائي مزود مُعَد. يحتاج الالتقاط التلقائي وتعلّم ملف المستخدم مزودًا يمكنه إرجاع مخرجات منظمة/استدعاء أدوات.

### الذاكرة مقابل AGENTS.md / وثائق المشروع

| خزّن في **الذاكرة**                                | خزّن في **AGENTS.md** / الوثائق الثابتة             |
| -------------------------------------------------- | --------------------------------------------------- |
| قرارات خاصة بالمشروع، أنماط أخطاء، «جرّبنا X وفشل» | قواعد وسير عمل مستقرة نادرًا ما تتغير               |
| تفضيلات المستخدم المكتشفة عبر الجلسات              | اصطلاحات البرمجة والعملية الدائمة                   |
| حقائق يجب أن تتبعك عبر المحادثات                   | تعليمات يجب أن يراها كل وكيل بغض النظر عن الاسترجاع |

قاعدة عامة: إذا كانت تعليمات مشروع دائمة، ضعها في AGENTS.md؛ إذا كان سياقًا ينمو من العمل الفعلي، دع الذاكرة (أو الالتقاط التلقائي) تحتفظ به.

### استخراج الذاكرة الذكي المستند إلى المطالبات

تلك العبارة في قائمة الميزات هي **الالتقاط التلقائي**: بعد محادثة، يلخّص طلب ذكاء اصطناعي في الخلفية العمل التقني ويحفظه كذاكرة. لا يلزم مطالبة خاصة منك. يستخدم `opencodeProvider` / `opencodeModel` عند تعيينهما، وإلا يرجع إلى `memoryProvider` اليدوي.

### ملف المستخدم

**ملف المستخدم** ملخص منفصل عبر المشاريع لكيفية تفضيلك للعمل (التفضيلات والعادات). يُحدَّث على فاصل زمني (`userProfileAnalysisInterval`، الافتراضي كل 10 مطالبات محلَّلة)، ويُعرض في عرض الملف في واجهة الويب، ويمكن قراءته عبر `memory({ mode: "profile" })`. لا تملؤه يدويًا للاستخدام العادي — تعلّم الملف يملؤه عندما يكون المزود جاهزًا. تتبع لغة المخرجات `autoCaptureLanguage` (الافتراضي `"auto"`، يعكس لغة مطالباتك)، وهو نفس الإعداد المستخدم للذكريات الملتقطة تلقائيًا.

**«لم يُعثر على ملف. استمر في الدردشة لبناء ملفك.»** هي الحالة الفارغة المتوقعة، وليست تعطلًا. يحتاج تعلّم الملف إلى:

1. تشغيل الالتقاط التلقائي مع مزود يمكن الوصول إليه (`opencodeProvider` + `opencodeModel`، أو رجوع يدوي كامل مع `memoryModel` + `memoryApiUrl`).
2. مطالبات جلسة كافية منذ آخر تحليل — على الأقل `userProfileAnalysisInterval` (الافتراضي **10**).
3. أن يدعم ذلك المزود المخرجات المنظمة/استدعاء الأدوات (نفس متطلب الالتقاط التلقائي).

إذا دردشت لفترة وما زلت ترى الرسالة، تحقّق من أن الالتقاط التلقائي يعمل فعليًا في السجلات وأن المزود المُعَد ينجح (تحليل الملف الفاشل لم يعد يختبئ خلف حالة فارغة عامة عندما يخطئ المزود).

### واجهة الويب

افتح `http://127.0.0.1:4747` لتصفح الخط الزمني للذاكرة–المطالبات، وفحص الالتقاطات، وإدارة ملف المستخدم. إذا ربطت الخادم خارج الحلقة المحلية، انظر [مصادقة HTTP Basic لواجهة الويب](#مصادقة-http-basic-لواجهة-الويب).

## أمثلة الاستخدام

```typescript
memory({ mode: "add", content: "Project uses microservices architecture" });
memory({ mode: "search", query: "architecture decisions" });
memory({ mode: "search", query: "architecture decisions", scope: "all-projects" });
memory({ mode: "profile" });
memory({ mode: "list", limit: 10 });
memory({ mode: "list-shards" });
memory({ mode: "migrate", fromPath: "/old/path/to/project" });
memory({ mode: "export", outputPath: "./memories.json" });
memory({ mode: "import", inputPath: "./memories.json" });
```

ادخل إلى واجهة الويب على `http://127.0.0.1:4747` لتصفح الذاكرة وإدارتها بصريًا.

**أمان ربط الشبكة:** أبقِ `webServerHost` على `127.0.0.1` ما لم تقصد تعريض الواجهة عمدًا. الربط بـ `0.0.0.0` (أو أي مضيف غير حلقي) يتطلب `webServerApiToken`؛ يجب أن ترسل جميع طلبات `/api/*` حينها `Authorization: Bearer <token>` أو `X-Opencode-Mem-Token`. افتح الواجهة بـ `?apiToken=<token>` حتى يخزّن المتصفح الرمز ويرسله.

ترحيلات الأبعاد تولّد كل تضمين جديد أولًا، وتستورده إلى جزء مفهرس مؤقت، وتتحقق من عدد الصفوف، ثم فقط تستبدل الملف الأصلي. الترحيلات الفاشلة تترك الجزء المصدر دون مساس.

## أساسيات الإعداد

الإعداد في `~/.config/opencode/opencode-mem.jsonc`:

**Windows:** `%USERPROFILE%\.config\opencode\opencode-mem.jsonc` (نفس مجلد `.config\opencode` أعلاه — وليس AppData). التخزين الافتراضي يُحل إلى `%USERPROFILE%\.opencode-mem\data` (صيغة `~` تتوسع إلى منزل المستخدم على Windows أيضًا).

ينشئ المكون الإضافي قالبًا كاملًا معلَّقًا في هذا المسار عند أول تشغيل. لكل إعداد وتعليق، انظر [`opencode-mem.example.jsonc`](opencode-mem.example.jsonc).

### التقاط رسائل الدردشة وحقنها (`chatMessage`)

تعيش هذه الإعدادات تحت المفتاح `chatMessage` في `~/.config/opencode/opencode-mem.jsonc`:

| ------------------------------------------------------ | ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `enabled`                                              | `true`           | التقاط مطالبات المستخدم المؤلفة وحقن سياق الذاكرة.                                                                                                                                                                                                              |
| `injectOn`                                             | `"first"`        | حقن سياق الذاكرة عند أول رسالة مستخدم في الجلسة، أو على `"always"` عند كل دورة مؤلفة.                                                                                                                                                                           |
| `maxMemories` / `excludeCurrentSession` / `maxAgeDays` | `3` / `true` / — | كم ذكرى يحمل السياق المحقون، وما إذا كانت الذكريات الملتقطة في الجلسة الحالية مستبعدة، وحد عمري اختياري بالأيام.                                                                                                                                                |
| `filterInjectedPrompts`                                | `true`           | تخطي نص المطالبات المحقون من المضيف أو من مكونات OpenCode الإضافية الأخرى (تذكيرات النظام، توجيهات التنسيق، إشعارات المهام الخلفية) حتى لا يُخزَّن أبدًا كما لو كتبه المستخدم.                                                                                  |
| `injectionMarkers`                                     | مدمجة            | علامات إضافية لتحديد الكتل المحقونة؛ تُضاف إلى القائمة المدمجة، ولا تستبدلها أبدًا.                                                                                                                                                                             |
| `captureChildSessions`                                 | `false`          | التقاط المطالبات من جلسات الأبناء للمنسّق (جلسات ذات `parentID`، مثل أبناء مهام/وكلاء OpenCode الفرعيين). رسائل «المستخدم» فيها يكتبها الوكيل الأب، وليس أنت، لذا افتراضيًا لا تُخزَّن ولا تُلتقط تلقائيًا ولا تُستخدم لتعلّم الملف ولا تُعطى سياق ذاكرة محقون. |

### اختيار / إعداد التضمينات

تشغّل التضمينات البحث بالتشابه للذكريات وملف المستخدم. أعدها في نفس الملف (`~/.config/opencode/opencode-mem.jsonc`). **لا توجد خلفية MLX** — التضمينات المحلية تستخدم `@huggingface/transformers` مع ONNX، وليس Apple MLX.

**محلي (الافتراضي):** عيّن فقط `embeddingModel`. عند أول استخدام يُنزَّل النموذج من Hugging Face ويُخزَّن مؤقتًا تحت `{storagePath}/.cache` (الافتراضي `~/.opencode-mem/data/.cache`).

**بعيد (متوافق مع OpenAI):** عيّن كلًا من `embeddingApiUrl` و`embeddingApiKey`. يستدعي المكون الإضافي حينها `{embeddingApiUrl}/embeddings` برمز Bearer. يقبل `embeddingApiKey` نفس صيغ الأسرار التي يقبلها `memoryApiKey` (`literal`، `env://…`، `file://…`).

| المفتاح                    | الدور                                                                                                                                      |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `embeddingModel`           | معرّف Hugging Face (محلي) أو اسم نموذج API (بعيد). الافتراضي: `Xenova/nomic-embed-text-v1`                                                 |
| `embeddingDimensions`      | تجاوز اختياري؛ عادة احذفه — تُستمد الأبعاد من خريطة مدمجة                                                                                  |
| `embeddingPooling`         | تجميع محلي: `"mean"` (الافتراضي)، `"cls"`، أو `"last_token"`. غير معيَّن → إعداد مسبق لنموذج معروف صغير أو `"mean"`                        |
| `embeddingQueryPrefix`     | بادئة لتضمينات مهمة الاستعلام. غير معيَّن → إعداد مسبق للنموذج أو Nomic عندما يكون `embeddingUseTaskPrefixes` صحيحًا. `""` صريح يعطّل      |
| `embeddingDocumentPrefix`  | بادئة لتضمينات مهمة المستند (نفس قواعد الحل مثل `embeddingQueryPrefix`)                                                                    |
| `embeddingUseTaskPrefixes` | الاشتراك الاختياري في بادئات Nomic `search_query:` / `search_document:` عندما تكون البادئات المخصصة/المسبقة غير معيَّنة. الافتراضي `false` |
| `embeddingDtype`           | تجاوز اختياري لنوع بيانات ONNX المحلي (مثل `"q8"`، `"fp32"`). عند التعيين، يُمرَّر إلى transformers.js `pipeline({ dtype })`               |
| `embeddingApiUrl`          | عنوان URL الأساسي لـ API تضمينات متوافق مع OpenAI (بدون مسار لاحق بعد `/v1`)                                                               |
| `embeddingApiKey`          | مفتاح API لتلك النقطة (مطلوب مع `embeddingApiUrl`)                                                                                         |

النماذج المحلية الموصى بها:

| النموذج                              | الأبعاد | ملاحظات                                        |
| ------------------------------------ | ------- | ---------------------------------------------- |
| `Xenova/nomic-embed-text-v1`         | 768     | الافتراضي؛ متعدد اللغات، سياق 8192؛ تجميع mean |
| `Xenova/jina-embeddings-v2-base-en`  | 768     | إنجليزي فقط، سياق 8192                         |
| `Xenova/jina-embeddings-v2-small-en` | 512     | أسرع، سياق 8192                                |
| `Xenova/all-MiniLM-L6-v2`            | 384     | سريع جدًا، سياق 512                            |
| `Xenova/all-mpnet-base-v2`           | 768     | جودة جيدة، سياق 512                            |
| `Xenova/bge-m3`                      | 1024    | متعدد اللغات؛ تجميع CLS تلقائي                 |
| `intfloat/multilingual-e5-large`     | 1024    | بادئات `query:` / `passage:` تلقائية           |

مثال — تضمينات OpenAI البعيدة:

```jsonc
{
  "embeddingApiUrl": "https://api.openai.com/v1",
  "embeddingApiKey": "env://OPENAI_API_KEY",
  "embeddingModel": "text-embedding-3-small",
}
```

مثال — bge-m3 محلي (التجميع الافتراضي CLS عبر الإعداد المسبق؛ تجاوز عند الحاجة):

```jsonc
{
  "embeddingModel": "Xenova/bge-m3",
  // "embeddingPooling": "cls",
  // "embeddingDtype": "q8",
}
```

تغيير `embeddingModel` أو الأبعاد أو التجميع أو بادئات المهام قد يتطلب إعادة تضمين الذكريات المخزّنة حتى تبقى متجهات التخزين والاستعلام متوافقة. فضّل اختيار نموذج (وإعدادات التجميع/البادئة) مرة واحدة والالتزام بها لمجلد بيانات معيّن.

**غير مدعوم — Intel Mac (`darwin/x64`):** يتطلب الاستمرار المحلي `@tursodatabase/database`، الذي لا ينشر ربطًا أصليًا لـ Intel Mac. إصدارات `onnxruntime-node` الثابتة (`1.24.1+`، بما في ذلك المثبّت `1.30.0`) تفتقر أيضًا إلى darwin/x64. استخدم Mac بـ Apple Silicon أو Linux أو Windows، أو نقطة نهاية بعيدة عبر `embeddingApiUrl` + `embeddingApiKey` (المثال أعلاه). على المنصات المدعومة، يثبّت `opencode-mem` `onnxruntime-node@1.30.0` (إصلاح تفكيك Ort::Env من `1.24.1` / #225) ويحمّل transformers عبر جسر حل CJS حتى تحافظ تثبيتات OpenCode المتداخلة على ذلك الربط. يُحل Transformers إلى مسار مطلق قبل تثبيت ذلك الجسر حتى لا يفشل مضيف OpenCode Bun `--compile` بـ `Cannot find module '@huggingface/transformers' from ''`. بعد الترقية، امسح ذاكرة التخزين المؤقت المتداخلة للمكون الإضافي في OpenCode (`~/.cache/opencode/packages/opencode-mem@*`) وأعد التثبيت.

### نطاق الذاكرة

- `scope: "project"`: الاستعلام عن المشروع الحالي فقط. هذا هو الافتراضي.
- `scope: "all-projects"`: استعلام `search` / `list` عبر جميع أجزاء المشاريع.
- `memory.defaultScope` يعيّن نطاق الاستعلام الافتراضي عندما لا يُوفَّر نطاق صريح.

### مصادقة HTTP Basic لواجهة الويب

عندما يُعيَّن `webServerHost` إلى أي شيء غير الحلقة المحلية (مثلًا `0.0.0.0`)، تصبح واجهة الويب قابلة للوصول لأي شخص على الشبكة. لإبقاء ذكرياتك بعيدة عن الشبكة المحلية، احمِ خادم الويب بمصادقة HTTP Basic عبر نفس ملف الإعداد المستخدم لكل شيء آخر:

```jsonc
{
  "webServerHost": "0.0.0.0", // optional: reach the UI from the LAN
  "webServerAuthPassword": "pick-a-strong-one",
  "webServerAuthUsername": "admin", // optional, defaults to the current OS user
}
```

| الحقل                   | الافتراضي                     | التأثير                                                                                                               |
| ----------------------- | ----------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `webServerAuthPassword` | _(فارغ)_                      | عند التعيين، يطلب الخادم بيانات اعتماد HTTP Basic Auth على كل طلب. اتركه فارغًا للإبقاء على السلوك المفتوح افتراضيًا. |
| `webServerAuthUsername` | مستخدم نظام التشغيل (`$USER`) | اسم المستخدم المطلوب لتحدي Basic Auth.                                                                                |

يقبل `webServerAuthPassword` نفس صيغ الأسرار التي يقبلها `memoryApiKey`:

- سلسلة حرفية (بسيطة، مناسبة للأجهزة الشخصية)،
- `env://SOME_ENV_VAR` لسحب القيمة من البيئة عند البدء،
- `file:///path/to/secret` لقراءتها من ملف (`chmod 600` موصى به — سيحذّر المكون الإضافي إذا كان الملف قابلًا للقراءة للجميع).

سيظهر المتصفح حوار Basic Auth الأصلي ويتذكر بيانات الاعتماد للجلسة الحالية؛ إغلاق جميع نوافذ المتصفح يتجاهلها، لذا يتطلب إعادة فتح المتصفح تسجيل الدخول مجددًا. تُقارن بيانات الاعتماد بفحص بزمن ثابت، وتحمل استجابة 401 غير المصادق عليها `Cache-Control: no-store` حتى لا تعيد أي ذاكرة تخزين وسيطة تشغيلها. يُرخَّى CORS أيضًا بمجرد تفعيل المصادقة، حتى تتمكن أدوات أخرى على نفس الشبكة المحلية من التحدث إلى API بعد المصادقة.

### مشاركة ذاكرة مشروع واحد عبر مستودعات متداخلة

افتراضيًا يُعرَّف المشروع بمستودع git المحيط، لذا يحصل كل
مستودع git فعلي على مخزن ذاكرة معزول خاص به. هذا خاطئ لـ
مساحات العمل متعددة المستودعات — الأشجار التي يديرها [`repo`](https://gerrit.googlesource.com/git-repo/+/HEAD/Docs/manual-repo.md) من Google،
أو monorepos، أو أي تخطيط تنتمي فيه عدة مستودعات git متداخلة إلى
مشروع منطقي واحد — لأن كل مستودع فرعي سيكون معزولًا.

ضع ملف علامة **`.opencode-mem-project`** فارغًا في جذر مساحة العمل:

```
my-workspace/
├── .opencode-mem-project   ← workspace root
├── kernel/                 (own git repo)
├── userspace/              (own git repo)
└── tools/                  (own git repo)
```

كل جلسة تبدأ في أي مكان تحت العلامة تُحل حينها إلى ذلك
الجذر وتشارك مخزن ذاكرة واحدًا، بغض النظر عن المستودع الفرعي الذي يعيش فيه
مجلد العمل:

```sh
touch ~/my-workspace/.opencode-mem-project
```

يُبحث عن العلامة بالمشي صعودًا من مجلد العمل الذي تمرّره بالفعل
كل مسارات الشيفرة (مجلد عمل المكون الإضافي، `process.cwd()` لـ web API)،
لذا الهوية **مدفوعة بالمجلد ومستقلة عن العملية**.
لا تعتمد على متغيرات البيئة أو قيمة إعداد عامة، والتي
ستكون غير موثوقة هنا: يعمل opencode-mem عبر عدة عمليات opencode
تشارك خادم ويب واحدًا، وبعض تلك العمليات فقط يحمل
متغير بيئة معيّنًا. مع العلامة، يُشتق جذر المشروع دائمًا من مكان
تشغيل الجلسة فعليًا.

تتقدم العلامة على اكتشاف git. عندما تكون موجودة، يُتجاهل
بعد remote git الخاص بالمستودع الفرعي عمدًا (سيصف مستودعًا متداخلًا
واحدًا فقط). بدون علامة، يبقى السلوك دون تغيير (هوية قائمة على git).

### نقل أو استعادة ذكريات المشروع

يربط opencode-mem أجزاء المشروع بمفتاح hash لهوية المشروع. نقل
مستودع (ترحيل نظام تشغيل، إعادة تنظيم مسار، التبديل من تركيب Windows
إلى مسار أصلي) يمكن أن ييتّم الجزء القديم تحت
`~/.opencode-mem/data/projects/` بينما يُنشأ جزء فارغ جديد للمسار
الجديد.

هذه استدعاءات أداة OpenCode `memory` بحجج JSON، وليست أوامر
لتشغيلها في الطرفية. رمز `memory migrate --from ...` بأسلوب القضايا يقابل
`memory({ mode: "migrate", fromPath: "..." })`.

**1. نقل محلي عندما ما زلت تعرف المسار القديم**

افتح OpenCode في مجلد المشروع **الجديد**. يجب ألا يحتوي المشروع الهدف
بالفعل على ذكريات (يُجهض الترحيل دون تغيير عند التعارض). عاين المصدر
والوجهة المكتشفة وإجراءات الملفات قبل تغيير أي شيء:

```typescript
memory({ mode: "migrate", fromPath: "/old/path/to/project", dryRun: true });
memory({ mode: "migrate", fromPath: "/old/path/to/project" });
```

للسلامة، يرفض الترحيل مصدرًا ما زال مجلد مشروعه المخزَّن
موجودًا. إذا أردت عمدًا نقل مصدر نشط، افحص مخرجات التشغيل الجاف
أولًا ثم مرّر `allowLinkedSource: true`. تُحتفظ ملفات جزء المصدر الأصلية
كنسخ احتياطية ذات طابع زمني `*.pre-path-migrate-*.bak`.

**2. المسار القديم ذهب — اكتشف الجزء اليتيم أولًا**

```typescript
memory({ mode: "list-shards" });
memory({ mode: "migrate", fromHash: "fa645294d88bbae2" });
```

يُبلغ `list-shards` عن كل hash مشروع، و`projectPath` المخزَّن، وعدد الذكريات،
والحالة (`current`، `linked`، `orphaned`، `missing-file`، `empty`، أو
`ambiguous`). `fromHash` هو `scopeHash` سداسي عشري صغير بطول 16 حرفًا
الذي يعيده هذا الاستدعاء. فضّله عندما لم يعد المجلد القديم موجودًا أو
تحتوي عدة أجزاء على نفس المسار المخزَّن، لأن الهويات القائمة على git
لا يمكن دائمًا إعادة حسابها من مسار مفقود.

**3. نسخ احتياطي / استعادة عبر الأجهزة**

```typescript
// on the source machine / old checkout
memory({ mode: "export", outputPath: "./memories.json" });

// on the destination machine / new checkout
memory({ mode: "import", inputPath: "./memories.json", dryRun: true });
memory({ mode: "import", inputPath: "./memories.json" });
```

يكتب التصدير مستند JSON بإصدار بدون متجهات. يعيد الاستيراد ربط
الذكريات بالمشروع الحالي ويعيد حساب التضمينات بالنموذج المُعَد
حاليًا. يضيف الاستيراد ذكريات إلى مشروع موجود، لكن معرفات الذاكرة المكررة
تجهض الاستيراد بالكامل قبل الكتابة؛ هذا يختلف عن `migrate`،
الذي يتطلب هدفًا فارغًا.

ملفات التصدير نص عادي ويمكن أن تحتوي على محتوى الذاكرة، وأسماء المستخدمين/عناوين
البريد، وعناوين URL للمستودعات، ومسارات مشروع مطلقة. خزّنها مثل النسخ الاحتياطية
الحساسة الأخرى واحذفها عندما لم تعد مطلوبة. تُحذف الإدخالات الخاصة بالكامل،
ولا تُضمَّن ملفات المستخدم وتاريخ المطالبات. يحتوي
المستند على `schemaVersion: 1`؛ ترفض عمليات الاستيراد إصدارات المخطط الأحدث غير المدعومة
بدل التخمين.

### مزود الذكاء الاصطناعي للالتقاط التلقائي

يشغّل الالتقاط التلقائي طلب ذكاء اصطناعي في الخلفية لتلخيص العمل التقني وحفظه كذاكرة. يحتاج أحد إعدادات المزود أدناه.

**موصى به:** استخدم مزودًا مصادقًا بالفعل في opencode ويدعم المخرجات المنظمة:

```jsonc
"opencodeProvider": "anthropic",
"opencodeModel": "claude-haiku-4-5-20251001",
```

يصدر المكون الإضافي طلبات مخرجات منظمة إلى API جلسة opencode بدل استدعاء نقاط نهاية المزود مباشرة، لذا يملك opencode المصادقة وتحديث الرموز وتوجيه المزود. يجب أن يطابق اسم المزود إدخالًا من `opencode providers list`، ويجب أن يدعم النموذج المحدد مخرجات JSON منظمة عبر opencode.

اختياريًا ثبّت متغير استدلال للنموذج بـ `"opencodeVariant": "xhigh"` (مثلًا لـ grok-4.7). يُطبَّق على استدعاءات LLM الداخلية للمكون الإضافي (ملخصات الالتقاط التلقائي، تعلّم الملف، تنظيف الملف)، بما في ذلك عندما يكون `opencodeModel` هو `"inherit"`، حتى يمكن للعمل الخلفي استخدام مستوى استدلال مختلف عن الجلسة التفاعلية.

نماذج الاستدلال البطيئة (أو مطالبات الملف الكبيرة جدًا) يمكن أن تتجاوز ميزانية المخرجات المنظمة الافتراضية البالغة 90 ثانية. عيّن `"opencodeTimeoutMs"` (بالمللي ثانية) لتمديدها لاستدعاءات المخرجات المنظمة الداخلية (ملخصات الالتقاط التلقائي، تعلّم الملف) — مثلًا `"opencodeTimeoutMs": 180000` لمدة 3 دقائق. تُقيَّد القيم إلى 10000..600000؛ يبقى الافتراضي 90000. تُحوَّل السلاسل الرقمية. يستخدم تنظيف الملف مهلة منفصلة أطول.

المزودون المدعومون: أي مزود يدرجه `opencode providers list` (مثل `anthropic`، `openai`، `github-copilot`، ...).

إذا عُيِّن `opencodeProvider` و`opencodeModel`، يتقدمان على إعدادات `memoryProvider` اليدوية أدناه.

**اتبع نموذج الجلسة:** عيّن `"opencodeModel": "inherit"` لاستخدام نموذج OpenCode ملموس وقت الاستدعاء بدل معرّف مثبت. لـ **الالتقاط التلقائي**، تُسجَّل كل مطالبة عبر خطاف `chat.params` ويعيد طلب الالتقاط استخدام مزود/نموذج تلك المطالبة. لـ **تعلّم الملف** ومسارات المخرجات المنظمة الأخرى (غير المرتبطة برسالة مستخدم واحدة)، يرجع `inherit` إلى أحدث نموذج في قائمة `model.json` الحديثة في OpenCode (مفضّلًا `opencodeProvider` المُعَد). إرسال معرّف النموذج الحرفي `inherit` غير صالح أبدًا وتسبب سابقًا في `ProviderModelNotFoundError: Model not found: <provider>/inherit` على تلك المسارات. ما زال `opencodeProvider` مطلوبًا كبوابة الإعداد العادية.

**الرجوع:** إعداد API يدوي (إن لم تستخدم opencodeProvider):

```jsonc
"memoryProvider": "openai-chat",
"memoryModel": "gpt-4o-mini",
"memoryApiUrl": "https://api.openai.com/v1",
"memoryApiKey": "sk-...",
```

**صيغ مفتاح API:**

```jsonc
"memoryApiKey": "sk-..."
"memoryApiKey": "file://~/.config/opencode/api-key.txt"
"memoryApiKey": "env://OPENAI_API_KEY"
```

أوضاع `memoryProvider` اليدوية:

- `openai-chat`: API متوافق مع OpenAI Chat Completions مع استدعاء أدوات/دوال. يمكن أن يعمل مع وكلاء متوافقين مثل LiteLLM فقط عندما يحافظ النموذج العلوي والوكيل المحددان على استدعاءات الأدوات.
- `openai-responses`: OpenAI Responses API مع مخرجات استدعاء دوال.
- `anthropic`: Anthropic Messages API مع استخدام الأدوات.
- `minimax`: نقطة نهاية MiniMax متوافقة مع Anthropic Messages. عيّن `memoryApiUrl` إلى النقطة العالمية (`https://api.minimax.io`) أو نقطة الصين (`https://api.minimaxi.com`)؛ يُطبَّق مسار `/anthropic/v1/messages` وترويسة `x-api-key` تلقائيًا. النماذج الحالية تشمل `MiniMax-M3` (سياق 1,000,000 رمز؛ تفكير تكيفي أو معطّل) و`MiniMax-M2.7` (سياق 204,800 رمز؛ تفكير دائم التشغيل). يدعم `MiniMax-M3` التفكير التكيفي عبر `memoryExtraParams`.
- `orcarouter`: بوابة نماذج متوافقة مع OpenAI بمعرّفات نماذج ذات مساحة أسماء. `memoryApiUrl` و`memoryModel` اختياريان — الافتراضي `https://api.orcarouter.ai/v1` و`orcarouter/auto` (اسم مستعار للتوجيه يختار نموذجًا قادرًا لكل طلب). إذا عيّنت `memoryModel`، استخدم معرّفًا ذا مساحة أسماء مثل `openai/gpt-5.5` أو `deepseek/deepseek-v4-flash`؛ يرفض OrcaRouter أسماء النماذج العارية. مثال:
  ```jsonc
  "memoryProvider": "orcarouter",
  "memoryApiKey": "<OrcaRouter API key>",
  ```
  يشغّل [OrcaRouter](https://www.orcarouter.ai) أيضًا أمانًا صفري الثقة على مستوى البوابة لوكلاء الذكاء الاصطناعي على نفس النقطة — فحص كل مطالبة/استجابة وحوكمة كل استدعاء أداة على أساس الرفض الافتراضي، دون تغييرات في شيفرة التطبيق.
- `atlas-cloud`: إعداد مسبق لـ OpenAI-compatible Chat Completions لـ [Atlas Cloud](https://www.atlascloud.ai). `memoryApiUrl` و`memoryModel` اختياريان — الافتراضي `https://api.atlascloud.ai/v1` و`deepseek-ai/deepseek-v4-pro`. إذا حُذف `memoryApiKey`، يُستخدم `ATLASCLOUD_API_KEY` من البيئة. مثال:
  ```jsonc
  "memoryProvider": "atlas-cloud",
  "memoryApiKey": "env://ATLASCLOUD_API_KEY",
  ```
  عند اختيار هذا المزود، تُرسل مطالبات الالتقاط التلقائي / الملف، واستجابات النموذج، وسياق المحادثة ذي الصلة إلى `https://api.atlascloud.ai`.

استكشاف الأخطاء:

- إخفاقات الالتقاط التلقائي لا تمنع استخدام أداة `memory` اليدوية.
- إذا أبلغ الالتقاط التلقائي أن مزودًا غير متصل، أكّد اسم المزود بـ `opencode providers list` وأعد ذلك المزود في opencode أولًا.
- إذا أعاد وكيل أو مزود مخصص نصًا عاديًا بدل مخرجات منظمة/أدوات، اختر نموذجًا/مزودًا آخر أو استخدم أحد أوضاع المزود اليدوية أعلاه.
- للنماذج التي ترفض `temperature`، أضف `"memoryTemperature": false` عند استخدام إعداد API اليدوي.
- للنماذج التي ترفض استدعاءات الأدوات المفروضة (`tool_choice: "required"`، مثل بعض أوضاع التفكير)، أضف `"forceToolChoice": false` عند استخدام `openai-chat` / `orcarouter` / `atlas-cloud`.
- لـ `opencodeProvider` / `opencodeModel` (مثل DeepSeek V4 thinking)، ما زال OpenCode يرسل `tool_choice` مفروضًا للمخرجات المنظمة. يعطّل opencode-mem التفكير على الوكيل الداخلي `opencode-mem-structured` (ويعيده في `chat.params` بعد دمج المتغير) حتى يكتمل الالتقاط التلقائي وتعلّم الملف. وكيل الدردشة التفاعلي لديك دون تغيير. إذا فشل الالتقاط ما زال بخطأ تفكير/`tool_choice`، اختر نموذجًا غير تفكير لـ `opencodeModel` أو أعد رجوعًا يدويًا كاملًا (`memoryModel` + `memoryApiUrl`).
- **`opencode-claude-auth` / Claude Code:** يستخدم الالتقاط التلقائي OpenCode مع مزودك `anthropic` المصادق. غالبًا ما يتكرر `format: json_schema` المفروض مع Claude-auth، لذا يستخدم opencode-mem مسار **نص-JSON** يحافظ على المصادقة لـ `opencodeProvider: "anthropic"` (بدون أدوات `StructuredOutput` مفروضة؛ تُحلَّل الرد بـ Zod). ما زال مراقب الخطوات يجهض الجلسات الداخلية الجامحة بعد خطوتين. إذا فشل الالتقاط ما زال، أعد رجوع Anthropic بمفتاح API يدوي كامل (`memoryProvider: "anthropic"` + `memoryModel` + `memoryApiUrl` + `memoryApiKey`) — لا يمكن إعادة استخدام Claude Pro/Max OAuth خارج OpenCode.
- **المنصات غير المدعومة:** Intel Mac (`darwin/x64`) غير مدعوم — `@tursodatabase/database` وإصدارات `onnxruntime-node` الثابتة (المثبّت `1.30.0`) لا توفّر ربطًا أصليًا لـ x64. استخدم Apple Silicon أو Linux أو Windows، أو نقطة نهاية تضمين بعيدة عبر `embeddingApiUrl` + `embeddingApiKey`. MLX غير مدعوم.

## صادرات المسارات الفرعية العامة

بالإضافة إلى نقطة دخول المكون الإضافي الرئيسية، يعرّض `opencode-mem` مسارًا فرعيًا مستقرًا واحدًا
يمكن لمكونات opencode الإضافية الأخرى استيراده مباشرة. هذا يتجنب الحاجة إلى
هندسة عكسية لاصطلاحات علامات الحاوية عند كتابة أدوات طرف ثالث تقرأ
أو تكتب في نفس مخزن الذاكرة.

### `opencode-mem/tags`

مساعدات علامات الحاوية القانونية. نفس الدوال التي يستخدمها opencode-mem نفسه
لتحديد نطاق الذكريات الملتقطة تلقائيًا.

```ts
import { getProjectTagInfo, getUserTagInfo, getTags } from "opencode-mem/tags";

// Canonical project tag derived from cwd (git remote URL if present, else
// the project root path). Format: `opencode_project_<sha16>`.
const projectTag = getProjectTagInfo(process.cwd()).tag;

// Canonical user tag derived from `git config user.email`.
// Format: `opencode_user_<sha16>`.
const userTag = getUserTagInfo().tag;

// Both at once.
const { user, project } = getTags(process.cwd());
```

العلامات التي تنتجها هذه المساعدات تطابق ما يكتبه الالتقاط التلقائي، لذا مكونات الطرف الثالث
التي تستدعي `POST /api/memories` ستصل إلى نفس الأجزاء التي يفهمها باقي
النظام بالفعل. العلامات اليدوية التي لا تحتوي سلسلتها الفرعية على
`_project_` أو `_user_` تنتهي في أجزاء ظلّية تفلترها `/api/stats` و
`/api/memories` بصمت — استخدام هذه المساعدات يتجنب ذلك المأزق.
